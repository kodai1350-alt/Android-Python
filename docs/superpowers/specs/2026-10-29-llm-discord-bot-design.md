# スマホLLMのDiscord Bot（Grok風）設計書

作成日: 2026-10-29
状態: ユーザー確認待ち（レビュー反映済み）

## 1. 目的と背景

ユーザーは、Xの「@Grok」のように、Discordでメンションして質問すると答えてくれるBotを作りたい。返事を作るLLMは有料のAPIを使わず、**自分のスマホ（ZenFone 4）の中で動かす**。スマホは Python Runner アプリ（このリポジトリ）でBotを24時間動かしている。

ユーザーが大事にしていること（ユーザーの言葉より）:

1. **自分が知らない分野でも分かる**こと。Grokの一番いいところとして挙げた。
2. 写真にメンションして質問すると答えてくれること。「メンションへの反応がいい感じ」なこと。
3. **全部無料**でやること。これは絶対条件。
4. 答えは**細かさ優先**。写真や資料を削って速くするより、時間がかかっても全部読ませる。

## 2. 利用者と利用シーン

- 使うのはユーザーと、サーバーの仲間。少人数の身内向けで、一般公開のBotではない。
- 例:
  - 誰かが載せた写真に返信して「@Bot これ何？」と聞く。
  - 「@Bot 量子コンピュータって何？」と、知らない分野について聞く。
  - 「@Bot 先週ラーメン屋の話したけど、どこだっけ？」と、前の会話を探す。
  - 「@Bot 10月20日に話してたゲームの名前なんだっけ？」と、日付を指定して探す。

## 3. 対象端末と前提

- Botを常に動かす端末: **ASUS ZenFone 4（ZE554KL）**、Android 8、Snapdragon 660（ARMv8.0、dotprod命令なし）。
  - メモリ量（4GBか6GB）は未確認。
  - **ZenFone 4で動かない場合**（メモリ不足、または遅すぎる）は、AQUOS sense6を24時間用の端末にする。写真やWikipediaを削ってZenFone 4に合わせることはしない（ユーザー回答）。
- 試験に使った端末: **AQUOS sense6（SH-M19）**、Android 13、Snapdragon 690、メモリ約5.5GB。ZenFone 4が手元にないときの代わり。
- Python Runner の現状（v0.2.4）:
  - 動かせるBotは1つ。**今動かしているBotは止めて、このLLM Botだけを動かす**（ユーザー回答）。複数Bot対応は待たない。
  - Pythonは3.14、pipが使える。
  - SQLiteは3.53.4で、FTS5とtrigramに対応していることを確認済み。
- LLMを動かす部分は llama.cpp（MIT、無料）。

## 4. 目標・非目標・アンチゴール

### 目標
- @メンションで質問すると、Discordの「返信」として答える。
- 写真について答える。質問に付いた写真も、返信先のメッセージの写真も読む。
- 知らない分野の質問には、**Wikipediaで調べてから**答える。答えには調べたページのリンクを付ける。
- 前の会話を探す。うろ覚えの内容、キーワード、日付指定の3通り。
  - 探す範囲は登録したチャンネルだけ。
  - 見つけた会話には元メッセージへのリンクを付ける。
- 返事は1通のメッセージを書き足しながら見せる（少しずつ文字が出てくる形）。
- 仲間が同時に使っても破綻しない。順番待ちを表示する。

### 非目標（今回はやらない）
- 有料のAPIやサービスを使うこと（LLM、検索、ホスティングのどれも）。
- 長い雑談や、何往復もする会話の文脈を覚えておくこと。
  - モデル（LFM3-VL）自体が複数往復の会話を推奨していない。
  - 返信先のメッセージは読む（後述）。
- 音声、動画への対応。
- 大人数の公開サーバーで使うこと。
- 登録していないチャンネルの会話を保存すること。

### アンチゴール（動いていても「失敗」とみなすもの）
- 調べもせず、もっともらしい嘘を自信満々に答える。小さいモデルなので、ここが一番の危険。
- 何通もメッセージを送って、通知を鳴らし続ける。
- 質問しても反応がなく、放置されたように感じる。
- お金がかかる仕組みが入り込む。無料枠のある有料サービスも含む。
- 登録していないチャンネルの会話や、Botのトークンが外に出る。

### 成功の基準
- 写真に返信して「@Bot これ何？」と聞くと、写真の中身を踏まえた答えが返る。
- 知らない分野の質問に、Wikipediaに基づいた答えとリンクが返る。
- 「先週の○○の話」を聞くと、該当する会話へのリンク付きで答えが返る。
- メンションしてすぐ（数秒以内）に、受け付けたことが分かる。

## 5. 振る舞い（ユーザーと合意済み）

### 5.1 質問の受け付け
- Botへの@メンションで受け付ける。登録していないチャンネルでも、メンションされれば答える。
- 返信の形でメンションされたら、**返信先のメッセージ（文章と写真）も読んで**答える。
- 受け付けたら、すぐにDiscordの「返信」として1通送る。
  - 「受け付けました」または「順番待ち 2番目です」と書く。
  - このメッセージを後で書き換えて返事にする。

### 5.2 返事の出し方
- 1通のメッセージを書き換えながら、文字を少しずつ見せる。
  - Discordの回数制限に引っかからないよう、1〜2秒ごとにまとめて更新する。
- 読み込み中は、経過を出す。例:「📖 Wikipediaを読んでいます… 60%」「🖼 写真を見ています… 30%」。
  - llama-server の `return_progress` で進み具合が取れることを、ソースで確認済み。
- 2000文字（Discordの上限）を超えたら、2通目に続ける。
- **返事は途中で切り上げない**（ユーザーが明確に「なし」と回答）。順番待ちの人がいても、最後まで書く。

### 5.3 待ち時間（ユーザー合意済み）
- 書き終わるまでの時間は問わない。
- 書き始めは「1分以内が目安」。ただし**細かさを優先**する。写真やWikipediaを削ってまで1分に収めない。
- 同時に聞かれたら順番待ちにする。1人1つまで。前の質問が終わってから、次を受け付ける。

### 5.4 写真
- 質問に付いた写真と、返信先メッセージの写真を読む。
- 画像を読むためのモデルが必要なので、写真も文字も **LFM3-VL-2B** 1つで扱う。
  - ZenFone 4のメモリでは、モデルを2つ同時に載せられないため。
- 写真の大きさは **512トークン（約730×730ピクセル）まで**（2026-10-29 ユーザー決定）。
  - 上限なしだと、カメラの写真は4096トークンになり、何十分もかかるか、メモリ不足で落ちた（実機で確認）。
  - 読んでいる間は「🖼 写真を見ています… 〇%（数分かかります）」と出す。

### 5.5 知らない分野（Wikipedia）
- 答える前にWikipedia（日本語版）を調べ、関係する部分を読ませてから答える。
- 答えの最後に、読んだページのリンクを付ける。
- 調べ先はWikipedia中心。Web検索は「使えたらおまけ」。
  - Google/Bingの公式検索は有料、または無料枠が小さい。
  - 登録なしの非公式な方法は、急に使えなくなる。

### 5.6 前の会話探し
- 探す対象は**決まったチャンネルだけ**（ユーザーの回答）。
- 対象チャンネルは、Discord上で管理者がコマンドで登録・解除する（例: `/記録する`、`/記録やめる`）。
- 登録したチャンネルは、Botを入れる前の古いメッセージもさかのぼって読み込む。
- 見つけ方の案:
  1. LLMが質問から、検索の言葉と日付の範囲を取り出す。
  2. 保存したメッセージから当てはまるものを探す。
  3. 見つかったものだけをLLMに読ませて答えさせ、元メッセージへのリンクを付ける。

## 6. 試験（スパイク1）で分かったこと

AQUOS sense6 での測定結果（v0.3.0-spike1）:
- モデル: LFM3-VL-2B QAD-Q4_0
- 組み立て: ARMv8.0向け
- llama-server 1スロット、4スレッド

| 内容 | 書き始め | 書き終わり |
|---|---|---|
| 短い質問（文字だけ） | 3.4秒 | 10.3秒 |
| Wikipedia 1500文字を読んでから答える | 149秒 | 166秒 |
| 写真（640px）について答える | 129秒 | 152秒 |
| 2人同時（文字＋写真） | 文字5秒・写真128秒 | 文字は写真の読み込み中ほぼ止まる（0.3トークン/秒） |

- 読む速さは約8トークン/秒、書く速さは約5.7トークン/秒（4スレッド）。
- 8スレッドにすると、書く速さが0.2トークン/秒まで落ちた。速いコアと遅いコアが混在するため。
- モデルの読み込みは3秒。
- 答えの質:
  - Wikipediaを読ませた答えは正確だった。
  - 何も読ませない答えはあいまいだった。
  - 写真はラーメンだと分かったが、変な言葉が混ざった（ナルトを「花形のタマネギ」と呼ぶなど）。
- **同時に2人分を書いても速くならない**。読み込みが全体を止めるため。→ 1人ずつ順番に処理する。
- ZenFone 4ではまだ測っていない。CPUの作りが違うので、数字は変わる。

## 7. 中身の仕組み

全体は2つの部分に分かれる。

### 7.1 アプリ側（Python Runner）: LLMを動かす部分
- **llama-server** をアプリに同梱する。
  - llama.cppをソースからNDKで組み立てる（ARMv8.0、API 26、静的リンク）。
  - スパイクではバイナリを直接コミットしたが、本番ではGradleかCIでソースから組み立てる。
- **モデルのダウンロード**:
  - Hugging Faceから、アプリ専用の場所にダウンロードする。
  - 途中から再開でき、サイズとハッシュを確認する。
  - 合計約1.25GB（本体 + 画像用のmmproj）。
- **起動と停止**: llama-server はBotと同じフォアグラウンドサービスで動かす。
  - Botを起動すると一緒に起動し、Botを止めると一緒に止める。
  - llama-server が落ちたら、立ち上げ直す。
- Botには、LLMの場所を環境変数（例: `LLM_URL`）で渡す。
- 起動設定:
  - `--reasoning off`。考える過程は出さず、すぐ答え始める。
  - 1スロット。
  - スレッド数は端末に合わせる（AQUOSでは4が最速）。
- アプリ画面: モデルの状態を表示する（未ダウンロード／ダウンロード中○%／準備完了）。

### 7.2 Bot側（Python、discord.py）
- メンションの受け付け、順番待ち、返事の書き換え（5.1〜5.3）。
- LLMへの問い合わせ: llama-server のOpenAI互換API（`/v1/chat/completions`）を使う。ストリーミングと `return_progress` を使う。
- Wikipedia: 日本語版のAPI（無料・登録不要）。User-Agentを付ける。
- 会話の保存:
  - SQLite（FTS5、trigram）。日本語のキーワード検索にtrigramを使う。
  - 保存先はアプリ専用の場所。
  - 共有フォルダには出さない。`.db` は既に「秘密のファイル」扱いでコピーされない。
- Discordの設定: Message Content Intent（メッセージ本文を読む権限）を開発者ポータルでオンにする必要がある。少人数のサーバーなので審査は不要。

## 9. 私（Claude）の判断で決めたこと
- モデルは LFM3-VL-2B 1つ（QAD-Q4_0 + mmproj Q8_0）。
  - 写真のためにVL版が必要で、メモリの都合で1つに絞った。
  - 遅すぎる、または日本語が不自然な場合は、同じ大きさの別モデル（Qwen3-VL-2Bなど）に差し替えられるようにする。
- 同時処理はしない（1スロット＋順番待ち）。スパイクの結果から決めた。
- 返事は1通を書き換えて見せる。何通も送らない。
- 経過表示（「Wikipediaを読んでいます… 60%」）。
- 登録はDiscordのスラッシュコマンドで行う。
- Wikipedia中心で、Web検索はおまけ。
- 会話はSQLiteのFTS5（trigram）で探す。
  - まずは言葉と日付で探す。
  - 意味の近さで探す仕組み（埋め込み）は、足りなければ後から足す。
- 前の会話探しの結果には、**質問した人が読めるメッセージだけ**を使う。
  - 質問されたのと同じサーバーの、登録チャンネルが対象。
  - 質問した人に閲覧権限があるチャンネルに限る。
  - 権限のないチャンネルや別サーバーの会話が、答えに混ざらないようにするため。
- 保存したメッセージはDiscordの状態に合わせる。
  - 削除されたメッセージは保存先からも消す。
  - 編集されたら、保存している文章も更新する。
  - `/記録やめる` をしたチャンネルは、保存したメッセージを全部消す。
  - 登録中は期限なしで保存する。
